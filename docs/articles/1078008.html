When developing an AI product, we faced an unexpected challenge. Choosing an LLM turned out to be easier than choosing an interface for it. Ready-made AI chats are well-suited for dialogue with a single model, but they start to limit the product when it includes multiple agents, complex scenarios, and intermediate work stages. In this article, we will describe the essence of the task, the requirements, and analyze Open WebUI.

The main goal of an MVP is to demonstrate the product concept and verify its viability. At this stage, it is important to focus on implementing core functionalities; the appearance is sometimes less important. However, in AI products, there is a nuance: even for an MVP, the interface often becomes part of the product's logic and future architecture.

If AI solutions used to be essentially a single chat where the user interacted with one neural network, modern solutions include a chain or graph of AI agents, each performing its task independently, sometimes interacting with the user. In this case, the UI becomes a full-fledged command center: system state, thought and work dynamics, tool calling, human-in-the-loop interaction points, and much more.

Therefore, the choice of a UI tool affects both prototyping speed and the final result, determining whether the user can organically work within the system. In this article, we will explain how we chose the frontend tool for the "Idea Bank" project.

What is "Idea Bank"?

"Idea Bank" is a multi-agent system responsible for analyzing and preparing employee ideas. An employee describes the problem they want to solve in a chatbot, submits their idea, and then it goes through multiple AI agents, each performing its assigned role:

  • Critic highlights weak points.

  • Security Officer removes confidential information before the idea is passed to an external LLM.

  • And other agents.

An AI agent is understood as an artificial intelligence-based system with a set of tools to solve the user's task.

While working on "Idea Bank," we encountered the need to quickly implement a frontend to demonstrate the service's functionality.

Technical Implementation

For the implementation of "Idea Bank," we used LangGraph, which allows representing agent logic as a graph: agent tools = nodes connected by edges forming the agent's pipeline, and each agent = a node in the overall orchestrator graph.

"Idea Bank" implies close user interaction as the idea evolves. We had a specific vision: we needed a familiar and intuitive interface: a chatbot with custom component integration.

What non-standard components were required:

  • Boards. At the stage of idea analysis by domain expert agents, each of them had to transfer their opinion to a board where the user could read them all, compare them, and even make their own edits. After the evaluation stage, the boards remained in the chat for context.

  • Graph Visualization. The full orchestrator graph pipeline takes 15 to 20 minutes to execute. To prevent the user from thinking the service is frozen, we wanted to display the progress of all agent work stages.

A standard chat interface works well when the entire result can be presented as a single stream of messages. However, if the system needs to show process states, pause for action confirmation, display tool results as interactive components, and maintain work context, the UI layer architecture is also important.

Tool Requirements

Based on the specifics of the task, we formulated the following requirements:

  • Open-source solution.

  • Ease of integration into an already created system.

  • Possibility of quick and convenient customization.

  • Professional and understandable interface.

  • Support for multi-step interaction.

  • Ability to display not only model responses but also intermediate states.

  • Suitability not only for demos but also for further development.

For internal MVPs, one can afford a temporary interface. But if the MVP shows good results, the business almost always wants to quickly move to a pilot with real users, and then to industrial implementation. An overly rigid UI framework might save time at the start but lead to expensive refactoring within a few weeks.

What We Tried

Based on the requirements, the list was narrowed down to two options:

  • Open WebUI — a self-contained open-source platform with a ready-made web interface for working with models, documents, tools, and knowledge bases.

  • Assistant-UI — an open TypeScript/React library that provides production-ready components and tools for building a chat, but assumes you assemble the product interface within your own application.

These are two tools for different scenarios. We compared them not directly, but by their convenience for development and the user, and the resulting business outcome.

Open WebUI

It was Open WebUI that we used for the first version of "Idea Bank" with a minimal architecture, and at first, it seemed like the best choice.
