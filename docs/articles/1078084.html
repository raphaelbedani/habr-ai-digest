Came up with it, consulted, implemented — the joys of rapid prototyping

Have you ever had a situation where a very interesting idea strikes you, coupled with the realization that you'll never implement it? Because you don't have time for it now, and you'll simply forget it later.

It was precisely in such a situation that I found myself while reviewing code from an analyst on my team.

📚 Task

We needed to identify clusters of users with characteristic behavior and, after examining them more closely, form a list of fraudulent schemes. The dataset is voluminous, with a large number of diverse features.

There are many ways to process these features and select those worth using for clustering. The thought of how much time such an analysis would take pained me.

💡 Idea

I thought, "It would be great if, at least for the first step, we could use an approach that works out-of-the-box with categorical features and is not sensitive to outliers" — and I felt that it sounded familiar. It sounds like a task for trees.

The thought of trees in unsupervised learning algorithms led my inner gaze to Isolation Forest — an anomaly detection algorithm based on a very simple but elegant idea: randomly partition a dataset into groups and see how often each observation is isolated from the majority.

Those that separate faster are likely very different from the rest. The principle of Isolation Forest can be seen below. I'm not very good at drawing, so I used Gemini. Sorry for the few labeling issues.

But this is anomaly detection, and we need to be able to find distances between objects to form clusters. The number of partitions here won't help: it only allows us to judge how similar an object is to all others.

But we can partition observations into subsets by randomly splitting features. After that, we can see how often two observations end up in the same subset. Something like this:

👨‍💻 Solution

With this idea in hand, I went to consult with the LLM. And the model significantly developed my idea, proposing an interesting approach to solving the problem of estimating object similarity. It suggested calculating cell IDs after obtaining random partitions as:

cell_id = Σ bj * Kj,

where:

  • j — feature number

  • b — bin number

  • K — number of bins into which features are divided

Thus, IDs will never repeat. The object's embedding (E) is a list of such cell IDs it fell into during different iterations.

The distance between objects A and B is calculated as Hamming Distance. Or simply the proportion of iterations in which two objects ended up in different cells. The more often objects fall into the same cell, the smaller the distance will be.

After that, any clustering algorithm can use the distance matrix.

5 minutes of discussion, and voilà — I get a library that is quite suitable as an MVP.

And it works! Not immediately: I had to fix a couple of bugs and go through several iterations of discussion — but it works, and I still haven't written a single line of code.

Testing on a toy dataset, or how likely are you to survive the Titanic

Let's try the approach on a dataset describing the Titanic passengers. It's small and has features of different types, making it an ideal candidate.

Here are the fields we can analyze:

  • PassengerId — unique passenger serial number.

  • Survived — binary target variable: 0 — deceased, 1 — survived.

  • Pclass — ticket socio-economic class: 1st, 2nd, or 3rd. Often serves as the main indicator of wealth.

  • Name — passenger's full name, including title or rank.

  • Sex — passenger's sex: male / female.

  • Age — age in years. For children under one year, a fractional value is indicated, e.g., 0.75 or 1.5. Missing values are present.

  • SibSp — number of spouses (husband/wife) and siblings traveling with the passenger.

  • Parch — number of children (children) and parents (parents) traveling with them.

  • Ticket — unique alphanumeric ticket number.

  • Fare — fare in pounds sterling.

  • Cabin — passenger's cabin number. A large number of missing values are encountered.

  • Embarked — port where the passenger boarded the ship. Takes three values: C — Cherbourg, Q — Queenstown, S — Southampton.

We will use only Sex, Age, SibSP, Parch, Fare, and Embarked as features. We'll use Survived and Pclass to see how they correlate with the found clusters.

Let's try just throwing them into the algorithm without any preprocessing — a paradise, easy and convenient:

fc = ForestClusterer(n_iterations=300,/ n_bins=3, quantile_cuts=True, n_clusters=3, corr_threshold=0.9, random_state=42,) labels = fit_predict(X)

And lo and behold, we got quite understandable clusters:

Cluster 1 consists almost entirely of women, mostly with family members. This explains the high survival rate.

Cluster 2 — with the highest concentration of 1st class passengers. This likely explains the second-best survival rate.

And Cluster 3 — men from 2nd and 3rd classes, mostly traveling without close relatives. These passengers had very little chance.

Interestingly, KMeans, trained on scaled data with OneHotEncoding, found completely different clusters:

🔵 Cluster 1 — mainly men from 2nd and 3rd classes with expectedly low chances of survival.

🟠 Cluster 2 — a higher proportion of women, more passengers with family members: higher chances. But these are 2nd and 3rd class passengers, which reduces the probability of survival.

🟢 Cluster 3 — 1st class passengers, and mostly women. The highest chances.

Overall, the dataset is not very well divided into groups, so within a relatively dense cloud, objects can be divided differently.

But if we add some anomalies, outliers that are significantly different from other observations, our algorithm will perform particularly well on such a "corrupted" dataset.

Let's see how Forest Clustering and a set of algorithms from sklearn highlight the connection between clusters and passenger classes.

We use the ARI (Adjusted Rand Index) metric — it evaluates the quality in machine learning: how well the clustering algorithm agrees with the true data labels — the reference classes. The metric eliminates random coincidences and allows for objective comparison of different algorithms. Learn more about it.

We are less interested in how strongly the clusters were related to the classes before adding outliers, and more in how the metric changed afterward.

We see that all algorithms except Forest Clustering showed a decrease in the strength of the connection. This indicates that our approach is more robust to outliers and, therefore, less demanding of data preprocessing.

What I'm getting at

Do not take this article as an advertisement for the algorithm or library; I perfectly understand that the algorithm has analogues, and the library is raw. This is just an illustration that with a couple of hours and an LLM, you can check an idea in passing without writing a single line of code.

Moreover, you can get a useful tool, albeit raw. In the case considered, it allows you to cheaply partition data using several algorithms without thinking about outliers, missing values, and categories.
