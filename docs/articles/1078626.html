Hello, Habr! My name is Ekaterina, I am a product designer and I am developing the "Sova" design system within the "Lukomorye" IT ecosystem.

We needed to connect design, tokens, and code at the component level. To do this, we had to describe each component in detail: sizes, variants, states, paddings, colors. Doing this manually can take a long time, so we handed over the mechanical part to the neural network. It didn't work out the first time.

Below is the entire process: how we exported components from Pixso, what we wrote in markdown files with rules and templates, and how we then checked that the neural network hadn't made anything up.

What are component tokens

To understand, let's break down tokens by levels. In our design system, there are three:

Base tokens are the initial values of the system: colors, sizes, paddings, radii, typographic parameters, and other primitives.

Semantic tokens, also known as aliases, are built on top of base tokens and add meaning to values. They make it clear where and why to use a specific color, padding, or style.

Component tokens describe the rules for a specific component: what colors, sizes, paddings, radii, states, and nested elements it uses.

The easiest way to show the difference is with a button.

A semantic token defines the role of a value: for example, error.default is used for an error or a dangerous action.

A component token specifies: in a button with an error state, the background uses the error.default color.

This applies not only to color. Size, padding, typography, radius, states, nested elements – for every significant combination, a rule must be described: what the token is responsible for and in which component variant it is used.

This sounds like a great way to quietly hate a task. The first few components feel exactly like that: a lot of manual checking and doubt. But then a base of understandable patterns, rules for the agent, and examples it can rely on emerges.

JSON as a way to describe a component

Another important term for this process is JSON export of a component. It allows you to formally describe a component: its name, type, sizes, states, and settings for color, borders, and other properties. This is convenient when data needs to be transferred to an agent from Pixso and then converted into a component token structure.

Throughout the article, I will constantly distinguish between two files – they are easy to confuse:

  • Component JSON export – a technical description of the original component from Pixso. This is what we give to the agent as input.

  • Final component token JSON – the structure of tokens that we create for the component. This is what we give to developers as output.

Why is a component layer needed

At first glance, it seems that semantic tokens are enough. The system already has roles: error color, main text, surface background, accent container. But they only describe the meaning of the value, saying nothing about where it is applied.

They do not answer the questions:

  • what alias to use for the button background;

  • what alias to put for the text inside the button;

  • what color should be in the disabled state;

  • what padding is needed for size m;

  • what rounding should the container have;

  • what changes on hover, pressed, or disabled.

Because of this, an empty space remains between semantic tokens and the actual component. A designer can choose the necessary styles in the layout, but their decision does not become a system rule at the code and component logic level.

Component tokens bridge this gap. They describe what values a component should use in each size, variant, and state. The designer gains the ability to fix component rules in a format that can be used in both design and code.

On the one hand, this provides more control: the component ceases to be a set of layers in the layout and becomes a described model with clear rules.

On the other hand, responsibility grows: if a component token exists, it becomes harder to say, "the developer misunderstood something." The rule is written, and it is precisely what developers, plugins, documentation, and the agent will read.

How the entire process looks

To avoid describing a component manually, we built the process around JSON export from Pixso. Seven steps:

  1. Select a component in Pixso.

  2. Generate a JSON export of the component using a plugin.

  3. Provide the AI with the JSON export, base and semantic tokens, token_rules.md, and a template example.

  4. Receive a draft of component tokens.

  5. Check the structure: axes, states, aliases, nesting, and extra properties.

  6. Refine the result manually.

  7. Provide the final component token JSON to the developers.

The AI handles the mechanical part: it parses the JSON export, collects the repeating structure, and suggests aliases. The final decision remains with the designer. It is necessary to check the token architecture, the meaning of aliases, controversial cases, and compliance with the actual component behavior.

What were the initial conditions

I won't lie, we didn't have a laboratory case with a design system in perfect condition.

The original web design system lived in Pixso. There was no ready-made library with variables already linked to components. At that time, Pixso did not support variables, so color and typographic styles were used within components, and sizes, paddings, and other parameters often remained raw numerical values.

JSON of base and semantic tokens for development already existed, but it described the lower level of the system: the main palette, semantic tokens, and raw values for paddings and other parameters.

Our task was to build a component token layer on top of this. And a problem immediately arose: how to transfer all component settings into a format that the AI would understand?

Describing it manually is unrealistic. The button in the example above is a small part of the nuances a component can contain. If other components are nested within an input, this hierarchy and dependencies must be correctly reflected in the component's implementation.

Here, JSON becomes our best friend. We developed a plugin that creates a JSON export of the component. The prompt can be viewed here.

What the agent will understand from such a button export:

  • the component structure, variants and states, hidden layers, and settings in Pixso;

  • the dimensions of each element, typography settings, and all nested elements;

  • the logic of the component's operation when switching states and variants.

How a component token is structured

Step one: Axes

For convenience, I will refer to size, variant, color scheme, and state as axes of our component token structure. They are formed from the component's variants and states. At the top level, properties are divided into two independent branches: size and variant.

The size branch stores geometry. Size has the greatest impact on other properties and values within the component. In the case of our button, the size property becomes one of the axes, and xl, l, m, and s are its values.

The visual branch variant is built in the order variant → colorScheme → state. The colorScheme axis does not change the button's structure, only the color scheme of the already selected variant, so it comes next, already within the variant axis. The last axis, state, changes the specific combination of variant and color scheme.

The final token name depends on the order of the axes:

button.size.m
button.variant.accent.primary.default

The size branch is responsible for geometry, the variant branch for appearance. Together they form one button.

What does not become an axis? Hidden layers like iconLeft and iconRight, as well as replacing a specific icon – they do not create separate axes. They control the visibility and content of the component.

In component tokens, such elements are described as if they are enabled by default. The developer determines which elements to show in a specific case during layout.

Step two: Populating with properties

Axes form the token path, but it's empty inside this address for now. Next, it needs to be filled with the properties we found in the component structure. A couple of hundred lines in the final JSON add component properties to each branch.

At this stage, it is important to record everything that the team actually wants to control through component tokens.

The logic is as follows: axes answer the question "for which combination does the rule apply?", and the content answers "what specific property and value are we setting in it?"

Step three: Populating with values

After the branches and properties are defined, each final token needs to be assigned a value. Each token contains three fields:

  • value – the direct value or a reference to another token;

  • type – the data type;

  • description – a clear description of the token's role.

In the value field, we must specify an existing alias, for example, interactive.accent, rather than the original color or number. If you use a raw HEX value, the settings will not be applied to the component when the alias changes. Remember the dependency chain: the component token stores a link to the semantic token, and that one to the base token.

Values must be set for each token, and the agent partially does this. It matches raw values from the export with design system aliases. If the value and semantic role match unambiguously, the alias is selected automatically. If multiple aliases correspond to one value or there is no exact match, the result must be checked manually.

You are responsible for thinking through the list of values that need to be controlled and correctly exporting the data.

Step four: Rechecking

After generation, I manually checked if the AI did everything correctly: axes, states, aliases, typography, raw values, and compatibility with real usage. Sometimes I uploaded the final JSON to Tokens Studio to check if all values were found. Tokens Studio is a Figma plugin that helps create, store, and apply design tokens.

What I look at first:

  • is the final JSON readable;

  • do the names conflict;

  • are the aliases correctly pulled;

  • are the links between tokens resolved correctly;

  • does the tool perceive any name as a service name.

The power of our vibe-coding environment here would be a quick assistant that would generate a structure in a couple of minutes, but would also quickly add five extra axes if not stopped 😄

There were many errors in the first generations, but after the fourth or fifth component, the structure stabilized, and fewer edits were needed.

  • template example of a component token for the most complex component;

  • token_rules.md with rules for creating component tokens and limitations.

How to make the chat's job easier

In addition to the JSON export, you can send a screenshot of the settings panel. Then the agent will resolve ambiguous points without your intervention.

For example, not everything decided in the design should be decided the same way in the code. I made the loading state in the component through a separate variant loading: true/false so that designers could enable it faster in the layout. In our adopted token structure, we describe loading as a state. By reading the screenshot, the agent will match the logic of the layout settings with the data from the JSON export and take this nuance into account.

Main errors and edge cases

Below are the most illustrative errors we encountered. The full list of rules, exceptions, and checks is collected in token_rules.md, which can be used as instructions for the agent and as a checklist when working with new components.

Do not add artificial complexity

If a component has only one size, there's no need to add an m group in the size axes. A structure without deep nesting is easier to read. You can always expand the token and add new sizes.

The same applies to unnecessary containers. If a layer adds nothing to the structure and the designer will not control it, there's no need to turn it into a separate token branch. Tokens should help manage the component, not create decorative bureaucracy.

Check nested dependencies

A component token, like a design system, is built atomically. If a component contains an independent reusable component, it is important not to duplicate its values but to maintain the dependency adopted in the system. If values are hardcoded without the base → semantic → component chain, changes to tokens will not be applied, and a bottleneck will appear.

For example:

  • input uses label and hint;

  • select uses label, hint, chevron;

  • segmented control consists of tab;

  • avatar can contain counter, status indicator, and action button.

Do not turn every property into an axis

Not all properties from Pixso or Figma should be included in the component token structure. Properties like iconLeft and iconRight, as well as replacing a specific icon, only control visibility and content. They do not change the component's architecture, so separate axes should not be created for them.

These elements are better accounted for as if they are enabled. Their sizes, paddings, and other controllable properties are transferred to the final JSON, but not the visibility toggles.

Do not transfer the entire export into tokens

The JSON export contains both useful properties and technical data from Pixso or Figma. The agent can conscientiously transfer everything it sees and create a huge structure that no one will use.

Before generation, it is important to determine what the team actually wants to control. If a property does not affect the component, does not change between its variants, and will not be needed for system configuration, it should not be transferred.

Do not invent aliases that do not exist in the system

If the agent cannot find a suitable alias, it may create a token that looks logical but is absent in the actual set. The rules should strictly prohibit the creation of new tokens.

Choosing an alias is important both for matching the value and for its semantic role. Two aliases can refer to the same color and be used in different scenarios. Such a value should not be silently accepted or replaced with raw HEX. If there is no exact alias or multiple suitable options are found, this decision is sent for manual review.

Be careful when matching typography

With typography, matching only by font size is not enough. Two styles can have the same fontSize and differ in weight, line height, or letter spacing.

We checked parameters in the following order:

  1. fontWeight

  2. fontSize

  3. lineHeight

  4. letterSpacing

If there is no exact match, the agent may suggest the closest existing alias, but such a decision must be explicitly marked for manual review.

What is in token_rules.md

token_rules.md is the main artifact of the entire process. It is a rule file that the agent reads before each generation.

Results

After design review, the final JSON is transferred to developers for technical integration. At this stage, the team looks not at the visual correctness of the tokens, but at how the structure fits into the code architecture: can variables be generated from it, does the naming match the adopted scheme, are there any conflicts in naming, types, and links between the semantic and component layers.

Some edits at this stage may no longer be about design logic, but about compatibility: somewhere a branch needs to be renamed, somewhere the token type needs to be clarified, somewhere a raw value should be left as a temporary solution until a new alias appears. Therefore, it is important to transfer not just "ready JSON", but a structure that clearly explains why the token appeared, which component it belongs to, and what decision lies behind it.

The first component – the button – took about one to two working days because most of the decisions were made from scratch. Then we took input. After the third component, a base of rules and ready examples emerged that the AI could rely on. Subsequent components took about 5-20 minutes, depending on complexity and the number of states. We made 45 components in total.

The mechanical work accelerated the most. The agent helped:

  • parsing the component's JSON export;

  • collecting the repeating structure;

  • finding suitable aliases;

  • filling in value, type, and description;

  • checking naming and unnecessary nesting levels.

The process did not become fully automated. We still manually define the token architecture, check the meaning of aliases, resolve controversial cases, and compare the final structure with the actual component behavior.

During the process, a common set of rules emerged: how to separate size and visual branches, what to consider an axis, how to work with a single size, hidden layers, and nested components. We collected these rules in a file so that subsequent generations do not start from scratch. Along with the JSON of component tokens, the file can be transferred to developers and used as a single source of agreements between design, code, and AI.

The main conclusion of the experiment: the agent needs high-quality input data, a clear template, and fixed rules. Without this base, it easily creates extra axes, confuses levels, and suggests a convincing but unsuitable structure for the system.

JSON helps to formally describe a component and transfer its structure to the agent. DESIGN.md explains how to assemble the final structure: what to consider an axis, how to choose aliases, where unnecessary nesting is not needed, and what decisions are worth checking manually.
