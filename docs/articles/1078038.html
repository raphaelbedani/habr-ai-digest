One broken bash script. Seven real bugs—from cosmetic (outdated filenames in comments) to fatal: a summary table that always shows zeros, no matter what actually happens.

Four models fix this script blindly, independently, unaware of what the other three are doing. Then, seven more models receive all four finished fixes as input and one task: assemble the best from them.

Spoiler alert—just enough to not spoil the intrigue: at the start, the models diverge much more than one might expect. No single model found everything. And their blind spots don't overlap. Therefore, the experiment is worth conducting rather than just discussing theoretically.

Introduction

In every task we give to a language model, there's a silently embedded question that is almost never asked aloud. Trust one model? Go find the best one? Run several in parallel and keep everything each of them caught? Or—one step further—give this whole pile of partial answers to another model and ask it to consolidate them?

Each answer is reasonable in its own way. Each is incomplete in its own way.

The point of this endeavor is to conduct an experiment, not to guess how it will end. There's one subject: a broken bash script with seven bugs of varying severity. The investigation proceeds in two rounds.

Round One: One Model, No Hints. Four models—Sonnet 5, HY3, Qwen3-Max, DeepSeek-V4-Flash—fix the script individually, each in its own bubble. This is the first frame: one model fixes exactly what it noticed itself.

The Best of Four. When four independent attempts lie side-by-side, the next question naturally arises: if you had to deploy only one of the four scripts to production, which one would you choose? This is analyzed in Table 1—although, here, "best" will be a synonym for "most complete," not "complete." Even the strongest of the four leaves actual bugs unfixed.

Round Two: Each Model Selects the Best from All Four. It is precisely this incompleteness that makes the second round meaningful. Seven models—ling-3.0-flash, Mistral-Medium-3.5, Nemotron-3-Super-120B, Qwen3-Max, DeepSeek-V4-Flash, Gemini Pro, dots-studio-3-note—receive the same four fixed scripts and the same task: for each bug, select the fix that is truly the best, regardless of its source, and assemble the selections into one script.

Who Actually Assembled Better. All seven are confident they picked the best pieces. That's exactly what the second round tests: will the model whose assembly is objectively stronger also be the one whose assembly appears stronger? Or will someone else among the seven, given exactly the same four scripts, assemble better than the obvious favorite? This is decided in Table 2, not here.

But the main finding lies not in the table headers, but beneath both. A script that simply works is not yet proof that the model found everything broken. A script that additionally explains its lineage—which fix came from where and why it survived—is proof of a different, much rarer kind. The difference between competence and honest handling of others' work—that's what these two tables actually reveal. We'll get to that in the finale.

What Kind of Script

run-code.sh is a bash wrapper: it calls codegen_test.py for a list of LLMs, collects results into a JSON file for each model, and prints a summary leaderboard table. The source code had seven real bugs—from cosmetic to fatal.

To understand who actually fixed what, not who claimed to fix it, each script was:

  • diffed line-by-line with the original;

  • syntax-checked using bash -n;

  • run with a stub codegen_test.py that outputs a realistic mix of statuses (PASS, TEST_FAIL, BAD_JSON, SYNTAX_ERROR, RATE_LIMITED)—so that the summary table output could be inspected rather than read through the code;

  • run on a real, flawed list of models—to check if the intentionally broken data still causes errors or not.

In the last step, the first version of the article featured a fictional preset OPENROUTER_FREE. Below, it's replaced with the script's actual OpenRouter preset, populated with IDs of models that are indeed live on the OpenRouter free tier as of August 2026—meta-llama/llama-3.3-70b-instruct:free, qwen/qwen3-coder:free, openai/gpt-oss-120b:free, openai/gpt-oss-20b:free, and nvidia/nemotron-3-ultra-550b-a55b:free—and directly cross-referenced with the OpenRouter blog and its live model catalog. The bug pattern doesn't change one bit; it's just that the illustration now relies on a real, verifiable provider, and the reader can check for themselves instead of taking my word for a fabricated gateway.

Next—what each bug looked like, why it's important, and then the two tables.

Bug #1—Corrupted Data Lines in OpenRouter Preset

In the original array, three corrupted lines were mixed among the working ones:

OPENROUTER_FREE=(    "meta-llama/llama-3.3-70b-instruct:free"          # <- suffix "|RPM|RPD" is missing entirely    "qwen/qwen3-coder:free|0|0"    "openai/gpt-oss-120b:free|0|0"    "openai/gpt-oss-20b:free|0|"                      # <- RPD field is empty    "nvidia/nemotron-3-ultra-550b-a55b:free|0|"       # <- RPD field is empty )

Further down the code, a loop parses each entry:

IFS='|' read -r MODEL RPM RPD <<< "$ENTRY" ... if [ "$RPD" -gt 0 ] && ...        # for corrupted lines, RPD here is an empty string

The script itself doesn't crash on [ "" -gt 0 ] (there's no set -e here), but bash dutifully prints bash: [: : integer expression expected to stderr for each corrupted line, and instead of 0 RPM / 0 RPD, there's a blank space on the screen. It's not fatal—but it's exactly the kind of noise that makes people stop trusting a tool's output. It's even more awkward because the actual rate limit for OpenRouter isn't model-specific at all: it's a flat 20 requests per minute and 50 per day (or 1000 per day with a $10 top-up) for the entire account. That's precisely why each live entry in this list should ideally read as |0|0, and the rate should be set by SLEEP_OVERRIDE.

How it was checked: each script was run with this OpenRouter list, and stderr was grepped for integer expression expected.

Bug #2—No Defensive Parsing for RPM/RPD

This is a generalized version of Bug #1: the loop blindly assumes that each |RPM|RPD field contains a clean, non-negative integer. There's no fallback for typos, missing fields, or manual edits to the list—and the OpenRouter free model registry is constantly edited by hand because the composition rotates: providers add and remove models.

A one-line guard handles both the specific typos above and all future ones the maintainer might introduce next month:

case "$RPM" in ''|*[!0-9]*) RPM=0 ;; esac case "$RPD" in ''|*[!0-9]*) RPD=0 ;; esac

or simpler:

RPM="${RPM:-0}" RPD="${RPD:-0}"

(Nuance: ${VAR:-0} triggers on an empty string as well as an unset variable—and it's precisely an empty string that read outputs for a missing field. This means this simple one-liner also neutralizes Bug #1 without touching the data at all.)

Bug #3—No Pre-flight Check for codegen_test.py Existence

The script sets a default:

SCRIPT="${SCRIPT:-codegen_test.py}"

…but never checks if the file exists before looping through 6–30 models and attempting python3 "$SCRIPT" ... for each. If the file is missing, you get a cryptic error on the very first iteration:

python3: can't open file 'codegen_test.py': [Errno 2] No such file or directory

…and so on, once per model, with no hint on what to do. A two-line guard before the loop turns this wall of text into a single clear message, after which it's immediately obvious where to go:

if [ ! -f "$SCRIPT" ]; then    echo "Missing script file: $SCRIPT"    echo "  Put codegen_test.py next to run-code.sh, or set SCRIPT=/path/to/codegen_test.py"    exit 1 fi

Bug #4—Summary Table Reads Non-existent Status Keys (Critical)

This one breaks the very purpose of the tool. codegen_test.py writes actual status values: PASS, TEST_FAIL, BAD_JSON, SYNTAX_ERROR, RATE_LIMITED. But the original summary block does this:

c = collections.Counter(r["status"] for r in recs) hall_rate = c["HALLUCINATION"] / n * 100 rows.append((hall_rate, -c["OK"], model, c, n, avg, min(times), max(times))) ... print(f"{model:<34} {c['OK']:>3} {c['HALLUCINATION']:>5} {other:>5} ...")

Counter returns 0 for a missing key instead of an error. Therefore, the code never crashes—it silently renders a useless table. Verified by running:

model                              OK  HALL  other  hall.%     min     avg     max ------------------------------------------------------------------------------------------ test-model-a                         0     0     3      0%    2.2s    2.8s    3.1s test-model-b                         0     0     3      0%    2.9s    3.4s    3.9s test-model-c                         0     0     3      0%    1.1s    1.2s    1.3s

All models have OK=0, HALL=0, and 100% are lumped into "other"—regardless of whether the model passed all tests or failed all of them. This is the entire point of the script (comparing models by code generation quality), and it was completely broken.

The correct fix must (a) know the actual status dictionary and (b) categorize it into meaningful buckets:

OK_STATUS     = {"PASS", "OK"} HALL_STATUS   = {"TEST_FAIL", "HALLUCINATION", "WRONG"} BROKEN_STATUS = {"BAD_JSON", "SYNTAX_ERROR", "MALFORMED", "PARSE_ERROR", "EXEC_ERROR"} INFRA_STATUS  = {"RATE_LIMITED", "TRUNCATED", "TIMEOUT", "ERROR", "HTTP_ERROR", "CONNECTION_ERROR", "API_ERROR"}

Bug #5—No Distinction Between "Everything Crashed" and "Some Attempts Failed"

if python3 "$SCRIPT" ... ; then    : else    echo ">>> ERROR on model: $MODEL"    FAILED+=("$MODEL") fi

codegen_test.py exits with a non-zero code if at least one attempt out of N fails—and this is a completely normal situation (a model that got 8 out of 10 showed a good result, not a crash). The original code doesn't distinguish between "this model got 8/10" and "this model had an invalid API key and nothing worked at all."

Verified in practice: with a mix of pass/fail statuses, every model was flagged as "error"—including those that mostly passed. For a benchmark, this is direct misinformation: the reader, glancing at the "errors" list, will assume these models are broken.

The fix should check if the results file was written at all before declaring a hard failure:

if [ "$rc" -ne 0 ] && [ ! -s "$JSON_OUT" ]; then    FAILED+=("$MODEL")          # nothing was written - a real failure elif [ "$rc" -ne 0 ]; then    DEGRADED+=("$MODEL")        # results exist, just some attempts failed fi

Bug #6—Fragile Summary Parser

with open(path) as f:    recs = json.load(f) ... model = recs[0]["model"]

If even one JSON file is truncated, empty, or missing a key (e.g., the run was killed mid-write), an unhandled exception will be raised here, killing the entire summary—for all models, not just the corrupted one. Fix: wrap risky parts in try/except and use .get() with a default value instead of bare indexing.

Bug #7—Outdated Documentation

The script was renamed at some point from run.sh to run-code.sh, but about 11 lines of comments and one hint in an error message remained untouched:

#   ./run.sh                      # free-tier Gemini, 3 attempts ... echo "  HOST=https://your-host/v1 PRESET=openrouter ./run.sh"

Copy this into a terminal—and you'll get "no such file." A small thing, but it's precisely these small things that create the impression of an abandoned script.

Round Two, or "Two from the Chest, Identical to Each Other"

Remember the cartoon? Vovka gets two workers from the chest, ready to do absolutely everything for him.

— And you'll do everything for us?! — Yep!

As is known, it ends with the two from the chest also eating for Vovka. Formally—the task is completed. In essence—the wrong thing was done.

Exactly this scenario plays out in the second round. Seven models receive four finished solutions from others and promise to assemble the best from them. Identical to each other: all seven produce syntactically valid, working, confidently looking scripts. The difference is not in who succeeded, but in what each of them quietly ate along the way.

Each of the seven was run through bash -n, through the same stress test with fake statuses, and again—on the real corrupted OpenRouter preset data.

Key Takeaways

  • No single model, no matter how strong, catches all bugs—each has its own blind spot, and these spots never overlap identically twice.

  • Strength in one area doesn't mean a model will even try another: the one that built the best summary logic never checked the data that summary reads. And vice versa.

  • A model that took first place in Table 1 still missed a bug that a lower-ranked model caught. Rank measures how many bugs a model found, not which specific ones.

  • Running multiple models in parallel and collecting all their findings yields more than any single model—but only if the one consolidating the results preserves the fix from a minority participant, rather than quietly discarding it.

  • A script that runs without errors is not proof that the model found everything broken: several of the worst bugs only surfaced when the scripts were actually run on real data.

  • Attribution in the task "assemble the best" is not a courtesy, but the only way for those further down the chain to ensure that the single successful finding from a weak source survived the merge.

Recommendations

  • For the isolated task "fix a bug": Qwen3-Max has the best "diagnosis → fix" ratio, and it defaults to defensive code (guards instead of data patches) even where I didn't specifically test for it.

  • For the task "merge and reconcile multiple outputs": Qwen3-Max again, with Gemini Pro as a strong alternative if you don't need explanations—just working code.

  • Do not use ling-3.0-flash, Mistral-Medium-3.5, Nemotron-3-Super-120B, and dots-studio-3-note specifically for uncontrolled merging: all four silently discarded the minority participant's fix without marking it in any way. This is exactly the mode of failure you don't want from a tool whose job is to "look at everything and assemble the best."

Finale: And You, Friends, No Matter How You Sit...

Let's step back from the code and imagine a manuscript. One meticulous author will always produce something coherent: Sonnet 5's script reads cleanly, comments are neat, intentions are visible line by line. But coherence is not the same as correctness, and the blind spot of a single editor remains blind, no matter how many times they reread their own draft. This is exactly what happened with the summary table, which no one thought to run.

A committee of editors catches more—the quartet of fixers proved that: among them, all seven bugs were found, each by someone.

But look closely at who found what, and the story becomes sharper than "the committee wins." Qwen3-Max fixed four out of seven bugs cleanly, topped both tables, and by any reasonable measure was the strongest model in the test. Yet, it didn't occur to it to check if codegen_test.py exists before looping through it. HY3—standing behind it in Table 1—figured that out. And was the only one out of the four who figured it out. First place didn't make Qwen3-Max the model that caught everything; it made it the model that caught the most. Each model here fixed something real. None fixed everything. And the bug that the final winner missed lay unclaimed in the very script that the winner surpassed in the ranking.

"And you, friends, no matter how you sit, you'll never make musicians."

Krylov, as usual, is precise—with one amendment for our case. The quartet's trouble wasn't that the musicians were bad, but that they kept switching seats, instead of someone listening from the outside and saying what exactly sounded off-key. Switching models—"let's take this one instead of that one, it's higher in the ranking"—is exactly the same seat-switching. Until someone listens to the result from the outside and compares it to the score, rearranging won't fix anything.

A committee is good only as far as the person holding the pen on the final pass is good: deciding which edit to keep, and—critically—being willing to write about it in the margins. Six out of seven assemblers kept the correct edits and remained silent about their origin. One kept the correct edits and documented the work. That's the entire difference between a model that merges answers and a model you can trust to merge them unsupervised. And precisely because no model, however strong, is self-sufficient, showing sources is not a courtesy. It's the only way for the next person in line to ensure that the single successful finding from a weak model didn't end up in the trash along with its worst mistakes.

Conclusion: Different Models, Verification, Continuous Checking

Three practical takeaways I'm taking from the experiment.

Different models are needed, not just one best one. Blind spots don't overlap—and this isn't a flaw of individual models, but a property of the landscape. The single model that caught the file existence check ranked second overall. Betting on one, even the strongest, performer is guaranteed to leave some bugs unfixed. Diversity here isn't about politeness to outsiders; it's about coverage.

Verification against hallucinations is needed. A model that writes "fixed" hasn't necessarily fixed it. Worse: Counter doesn't crash on a non-existent key, [ "" -gt 0 ] doesn't bring down bash without set -e, and a model's report on its own work always sounds confident. These are all silent failures that can't be caught by reading code. They are only caught by running: diff with the original, bash -n, run on a testbed with realistic statuses, run on intentionally corrupted data. A model's report is a hypothesis, not a result.

Continuous checking of all models is needed, not just the winner. The temptation is understandable: identify the leader and then only look at them. But rank indicates how many bugs a model found, and is silent on which ones. The single instance of a needed fix might lie with an outsider—and if you only check the favorites, that needle will remain in the haystack.

That very needle from the first round—the pre-flight check for $SCRIPT—was found by exactly one out of four models, and not the winner. It got lucky: in the second round, all seven assemblers picked it up. Sonnet 5's documentation cleanup was less lucky—four out of seven assemblers discarded it silently, and none mentioned it. The difference between these two fates is pure chance, not a merit of the process. That's precisely why you need to look at everything: every contribution, every merge, every line that quietly didn't make it to the final file. And that's why an assembler that provides a "fix → source → line" table is more valuable than six who delivered the same working script silently: it turns finding a needle into checking a list.
