CMF: A New Format for Creating Specialized LLM Models

CMF is a new format for neural networks. This article explains how CMF differs from GGUF and SafeTensors, and how multiple capabilities can be layered onto a common structure without storing separate full models. General-purpose language models can solve many tasks, but this universality comes at a cost: they are large, heavy, and contain many intertwined capabilities at once. I wanted to learn how to take an already trained LLM and compile it for a specific job, resulting in a compact specialist that can be run on cheaper hardware.

At the same time, one universal model could serve as the basis for an entire family of such specialists, with automatic selection of the appropriate one for each query.

It is important to clarify: by "compilation" here, I mean not exporting weights or uniform bit-depth reduction. Standard compression answers the question "how to store the same weights with fewer bits?", while task-specific compilation answers a different question: "what computation is actually needed for the chosen class of tasks?"

The system design was similar to Mixture-of-Experts (MoE), but with one key difference: the experts were to be not individual blocks within one large network, but independent models.

                                   │
                                   ├─ math specialist
                                   │
                                   ├─ document specialist
                                   │
                                   └─ general-purpose model, if unsure
request ──► router ──────────

I already had the router technology – now you can use the Allaigate Routing API via API. It determines the type and complexity of the request, estimates the confidence of the choice, and the system owner decides which model (local or cloud) to match it with. It can be used with my development Cortiq-gateway and a plugin for DeepSeek Harness (I will write a separate article). Essentially, this is request-level routing – a kind of MoE operating over a whole fleet of LLMs.

The main component was missing: a way to obtain such expert specialists directly from an already trained model.

I didn't come up with the first verification task myself – I asked for suggestions on a forum. I was asked to solve first and second-order differential equations. This turned out to be a good test: it's not enough to just make the model smaller – the specialist had to perform significantly better specifically in the domain for which it was выделен.

After the experiment (Qwen3.5 0.6B), about 20% of the original weights remained active, and there was a pleasant surprise that the quality on this task, according to the metric used then, increased several times. It's easier to explain it this way: imagine a hall of different specialists, and we keep only those specialists who are responsible for a specific task, while the rest of the unnecessary "noisy" specialists leave, increasing accuracy.

Next, I faced the question: how to store and execute such a network without turning the zeroed weights back into gigabytes and without destroying the consistent structure of connections between tensors? The answer was CMF (Cortiq Model Format) and the Cortiq executor. Deciding to develop my own format was quite difficult; I imagined how much work would be required, and decided to approach it thoroughly. First, I thought about the architecture and flexibility of the format, plus I already had several of my own discoveries and patents in the field of AI that I decided to implement.

This is the first detailed open publication where CMF is presented as a standalone format. I developed the specification, converter, executor, computational kernels, and mobile path alone from the first prototype to the current state. The project is now open – and further in the article, I clearly distinguish between what has already been implemented, tested, and measured, and what still requires independent verification. Four Levels of a Single System

To avoid confusion between different project components, it is more convenient to divide them by purpose:

Component

Purpose

DTG-MA and skill bake

Extracts the task mask from the general model and training corpus, restores specialist quality, and physically removes inactive structures if necessary.

CMF

Stores the resulting structure: tensor shapes, masks, skills, linkage to the general base, quality metrics, origin information, and integrity checks.

Cortiq

Loads and executes CMF files on CPU/GPU, provides a local OpenAI-compatible API, and can distribute layers across devices.

CMF emerged at the intersection of the first two levels. The task compilation method already created a structure that a standard dense weight file described incompletely – the new artifact required its own clear rules for storage and execution.

How a Task Corpus Becomes a Specialist

The current task compilation workflow looks like this:

trained LLM + task corpus
        ↓
L1-regularized mask of active FFN coordinates
        ↓
optimization by error on a hold-out set
        ↓
FCD: fine-tuning of the last layers with a precise teacher
        ↓
defrag (physical removal of inactive neurons)
        ↓
standalone CMF specialist

The mask is applied consistently: the same active intermediate coordinates are marked simultaneously for gate_proj and up_proj, as well as for the corresponding columns of down_proj in FFN. With increased L1 regularization, some neurons are gradually turned off. Initially, this often improves the result – the network gets rid of connections irrelevant to the domain – and then the quality begins to drop sharply.

The key rule here is to preserve the point of minimum quality on the hold-out set, rather than the mask that yielded the most aesthetically pleasing removal percentage.

The effectiveness of the approach strongly depends on the domain: where the base model is initially weak in a certain subject area, task compilation usually helps. (I will soon write a detailed article on how to create your own specialized models using financial market forecasting as an example)

Why Standard Compression Was Insufficient

I tried saving the first version of the specialists in GGUF format. The choice was logical: GGUF is a mature, self-describing format, well-suited for mmap, stores the tokenizer, metadata, and relies on the vast llama.cpp ecosystem.

The problem appeared immediately after task compilation. A large portion of the weights became zero, but the dense tensor did not decrease in size – a zero value in a file takes up exactly the same number of bytes as a non-zero value of the same bit depth.

The obvious solution is to pack only the non-zero values more densely. In practice, this ran into the issue of tensor axis consistency. In a classic FFN, an intermediate coordinate is rigidly linked across three projections: it corresponds to the rows of gate_proj and up_proj and simultaneously to the column of down_proj. In MoE, router rows, expert numbers, and active expert selection rules are added to this linkage. If a coordinate is removed or reordered in only one of these matrices, the computation of the entire network becomes incorrect.

I tried various approaches: packing sparse values, consistent row and column permutations, aligning masks between layers, removing rarely used MoE experts. The file did become smaller, but stable quality preservation proved unreliable. The reason was not in the specific container – task specialization requires its own execution semantics.

One could add custom fields to GGUF, but a single new field would not teach the existing executor to read task masks, substitute tensors with skills, check compatibility with the base model, or physically skip removed structures. In any case, a new loader and, essentially, new execution logic would have to be written. Therefore, it was more honest not to try to "fit" GGUF to this semantics, but to clearly define all necessary rules in a separate format.

Two Ways to Save a Specialist

CMF implements two fundamentally different ways of storing the specialization result. They address different practical scenarios: an autonomous single specialist or a family of specialists on a common base.

1. Autonomous Specialist – Physical Removal

If the model is intended for only one task, unnecessary FFN neurons can be physically removed. On disk, smaller tensors are stored instead of the original large ones: the number of rows for gate_proj and up_proj becomes equal to the number of columns for down_proj. The size can vary for different layers.

This is not about zeroing out or truncating bytes. The algorithm works as follows: the original tensor is dequantized, only the "live" (active) coordinates are consistently selected from it, then the resulting smaller matrix is quantized anew, with recalculation of the scale and obtaining a new hash. For MoE, entire unused experts are removed similarly, along with the corresponding router rows. After this operation, the unnecessary weights truly do not exist – neither in the file nor in the computation.

2. Multiple Specialists – Common Base and Skills

If one base model needs to serve multiple different tasks simultaneously, the base cannot be physically cut out: weights that are useless for one specialist may be critically important for another.

In this case, CMF uses task masks and replacement tensors – "skills".

  • The mask is packed bitwise and marks which specific FFN neurons, attention heads, layers, or MoE experts should be considered active for a given task.

  • Common weights are never duplicated. The mask simply determines which part of the unified base to use when executing a specific skill.

  • The skill (skill.<name>.<tensor>) stores only those tensors of full logical shape that differ from the common base. It is neither a second full model nor a classic LoRA adapter (although conceptually related to them). During the forward pass, the executor selects the source for each tensor: either the original base or the tensor of the corresponding skill.

As a result, storage cost looks like this:

size of common base + sum of actually changed tensors of all skills,
not (number of skills) × (size of full model).

An inactive skill is not loaded into RAM and does not consume computational resources. Each individual skill file is rigidly linked to its base via the base_dir_hash field – this prevents errors when applying a skill to a similar but differently quantized or otherwise modified model.

CMF can also store a small descriptor of the hidden state subspace (latent space descriptor). Based on the reconstruction error of the hidden state, the executor can automatically select the most suitable skill, mix the two best, or switch between skills directly during generation. This introduces a second level of routing: Allaigate selects a model from the fleet, and CMF selects a suitable capability within the chosen common base.

This analogy with a classic compiler has an important fundamental difference. A program compiler must fully preserve its semantics. Task compilation of a model, however, guarantees the preservation (and usually improvement) of quality only on the specified target task distribution. This is why the CMF specification does not allow specifying a default "quality 1.0" – quality metrics are recorded only with a specific measurement, hold-out set, and its checksum. If a measurement was not performed – the corresponding field remains null.

CMF on Disk: Predictable Structure and Strict Checks

The CMF v2 specification is built on the principle of "minimum magic, maximum verifiability." The file begins with a fixed 128-byte envelope containing the addressing of all sections. Thanks to this, the reader never calculates offsets manually – the structure is completely self-contained.

The overall file layout is as follows:

128 bytes: envelope and section table
        ↓
JSON: architecture, origin, chat template, skill registry
        ↓
binary tensor directory: name, type, shape, offset, length, hash64
        ↓
weights block, aligned for efficient mmap
        ↓
optional sections: masks, tokenizer, index, etc.

The weights block is aligned to a 4096-byte boundary, and each tensor to a 64-byte boundary. This allows the CMF file to be memory-mapped entirely via mmap: pages that have not yet been accessed are not physically loaded into resident RAM.

Each tensor has a 64-bit hash of its content. The directory, header, and optional sections are protected separately. The cortiq verify command checks the correctness of all boundaries, alignments, and the complete integrity chain. Such a check reliably detects file corruption.

Integrity control is separated from authorship confirmation. For the latter, the format includes a separate Ed25519 signature over SHA-256 of the entire file – these two mechanisms are intentionally not mixed.

CMF can also store the tokenizer and chat template directly in the same file. The executor applies the dialogue template recorded in the model and relies on the end-of-generation (EOS) identifiers recorded in it, rather than relying on hardcoded assumptions about the model family.

Bit Depth – Not Global, but Pointwise

The convenient approach of "making the entire model 4-bit" doesn't always work. Different tensors have different sensitivities to quantization: small control matrices, normalizations, and key tables are usually more sensitive than large dense matrices. In CMF, the quantization type is specified for each tensor separately, and in MoE – also for each expert.

Below are the codecs that appeared in response to specific practical problems:

Codec

Stores

Purpose

q8_2f

Integer values and two scales: for output matrix rows and for input channels (w = q · s_row · s_col)

Allows for more precise handling of outliers without forcing a single row scale to cover the entire row.

q4tp

4-bit values and a 5-bit geometric scale step

Provides ~4.17 bits per weight instead of ~4.50 for q4t, while maintaining the same 4-bit quantization grid.

q2tp

2-bit grid of 4 levels with a predicted scale; the zero step encodes an exact zero

Useful for compact profiles with redundant MoE experts: removed groups do not return as small noise.

vbit_ro

3 to 8 bits per row with a table of row offsets

Allows uneven distribution of the bit budget (more bits for important rows) while maintaining O(1) access to any row.

q1 / q1t

Binary (q1) and ternary with a dedicated outlier layer (q1t) representation

Intended for models specifically prepared for extremely low bit depths. Aggressive 1-bit quantization should not be considered unconditionally equivalent to the original weights without measurements.

The flexibility of bit-depth distribution does not negate the need for quality measurements. Two files of the same size can distribute quantization error very differently. The format provides building blocks – the specific quantization profile should always be chosen based on quality verification on relevant data.

O(1) Attention: Constant KV Cache Size

The volume of the KV cache in classic precise attention grows linearly with context length: each new token adds keys and values that will be needed for all subsequent generation steps. In long dialogues, it often happens that the model still fits in memory, but the dialogue history no longer does.

In Cortiq, the --o1 mode replaces selected layers of precise attention with a streaming attention operator with a fixed state budget. It stores a few precise anchor keys, a recent precise window of tokens, and a compressed representation of the older part of the context. After reaching the specified budget, the state volume stops growing with the increase in the number of processed tokens.

It is important to clearly state the limitation here: this is approximate attention. When --o1 is enabled, the model weights do not change and retraining is not required, but the model's behavior (and thus generation quality) may differ from precise attention. Therefore, this mode is recommended to be enabled only after measurements on a specific model and specific tasks. If necessary, a separate FCD stage allows fine-tuning the transformed layers and leaves the result in CMF only after generation verification.

CMF stores parameters and hints for this mode, but the O(1) behavior itself is implemented exclusively in Cortiq. Another reader of a CMF file will not automatically get streaming attention – this is part of the execution semantics, not a declaration in the format.

One Container – Not Just for Text LLMs

The CMF directory is not limited to text model decoders. Multiple components of a multimodal pipeline can be stored in the same address space: a text encoder, a diffusion transformer, a VAE, an audio decoder, configurations, a tokenizer, and other modules.

For example, the published model MiniMax-H3 Turbo combines a diffusion transformer, a Qwen3-VL query encoder, a video VAE, and audio components in a single .cmf file. The cortiq animate command generates video with a synchronized stereo track from a single text (or multimodal) prompt. Similarly, image generation is implemented for Lumina, and video generation for LTX-2.5.

It is precisely in multimodal pipelines that a unified container has provided a particularly noticeable practical benefit. A working build of MiniMax-H3 as separate source files, intermediate artifacts, and utilities occupied about 200 GB. A ready-to-run pipeline in CMF is distributed as one file: 14.48 GB in a compact version or 25.70 GB with a full query encoder. This is not about "compressing the model 14 times," but about replacing an entire set of files required for launch with a single verifiable, self-contained artifact.

It is important to understand the boundary: CMF stores components and their precise architecture description, but does not magically implement any architecture. Cortiq must be able to build the corresponding computational graph for these components. The separation between the format (storage and description) and the executor (computation) is strictly observed here.

The recommendation is simple: if maximum compatibility with existing local models and hardware is needed, GGUF is the more logical choice today. If you are transferring "raw" tensors between libraries, use SafeTensors. CMF is designed for a different class of scenarios: a ready-made specialist (or family of specialists) obtained through task compilation, carrying multiple capabilities on a common base, with step-by-step verifiability and the ability to execute without a heavy ML library.

Cortiq supports CPU inference, uses Metal on Apple Silicon, and wgpu (Vulkan/DirectX 12) on GPUs where this platform is supported. On verified architectures and models, generation quality with comparable settings has been brought close to llama.cpp. This statement applies specifically to verified configurations, not to a promise of exact logit matching, performance, or support for any new architecture.

Quick Start: Try in 1 Minute

The Cortiq converter is written in Rust and does not require Python or PyTorch. It can take a model either from a local folder in Hugging Face format or by its repository ID on the Hub.

Install the CLI:

cargo install cortiq-cli

Convert a small model to CMF with q4tp quantization:

cortiq convert \
  --model Qwen/Qwen3-0.6B \
  --quant q4tp \
  --output qwen.cmf

Verify the file integrity:

cortiq verify qwen.cmf

Run generation in the terminal:

cortiq run qwen.cmf \
  --prompt "Explain the difference between mmap and regular file reading" \
  --greedy --no-think

The same file can be served as a local OpenAI-compatible server:

cortiq serve qwen.cmf --port 8080

If you already have a model in GGUF format, you can import it directly into CMF, without intermediate steps in Python:

cortiq import-gguf model.gguf --quant q4tp --output model.cmf
cortiq verify model.cmf

The CMF v2 specification, an independent Python reader, and all Cortiq source code are published in the project repository under the Apache 2.0 license.

Why I Am Publishing the Project Now

Until now, I have consciously refined the entire chain alone: the format, the converter, execution on CPU and GPU, the mechanics of skills on a common base, streaming attention, multimedia, and mobile launch. This approach allowed for rapid changes across all system levels while key architectural decisions were still being solidified.

Now, solo development has become more of a limitation than an advantage. The format needs independent readers, testing on various hardware, and testing on models and tasks chosen not by the author. The contribution of those who are willing to:

  • Add and test support for new LLM/VLM architecture families;

  • Improve computational kernels for Metal, Vulkan, and DirectX 12;

  • Conduct independent comparisons of quality and performance with llama.cpp and original SafeTensors;

  • Develop task compilation methods: masks, skills, working with MoE experts;

  • Test and refine network distribution of the model on different phones and computers.

The methods underlying the project are described in four US patent applications: No. 19/452,440 (request routing), No. 19/452,464 (task-driven compression), No. 19/731,402 (multiple specialists on a common base), No. 19/738,763 (streaming attention with constant memory footprint). The exact link of these applications to the project code is provided in PATENTS.md.

The code is distributed under the Apache 2.0 license, and Section 3 of this license grants users a patent license for those patent claims that are inevitably implemented by the distributed source code.

The next stage is independent experiments on other models, domains, and hardware platforms.
