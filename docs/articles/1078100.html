Recently, businesses have been increasingly looking towards Agentic AI – systems where neural networks don't just respond to prompts in a chat but act as autonomous digital employees.

When it comes to large enterprises, compliance, and working with sensitive data (e.g., legal or financial documents), cloud APIs from OpenAI or Anthropic immediately become a showstopper. Security demands complete isolation.

In this article, I will technically break down how we designed and implemented the "Archangel" On-Premise multi-agent AI platform, capable of operating without external internet access.

1. Delivery and Infrastructure Layer: Full On-Premise in Kubernetes

For large customers, it is critically important that software is deployed within their own isolated perimeter (On-Premise) and managed using tools familiar to their Ops teams. We abandoned complex proprietary installers in favor of containerization.

We deliver the "Archangel" platform as isolated Helm charts for the customer's Kubernetes cluster. This ensures predictable deployment and easy scaling under load. Isolation is provided not by the packaging itself, but by network policies and the absence of an external route – more on this below.

How it works at the infrastructure level:

- Air-gapped environment. All platform's base Docker images and local LLM weights (e.g., Llama or Mistral families, adapted for our tasks) are mirrored to the customer's internal private registry – Harbor or Nexus.

- State and Storage. Within the Helm charts, StatefulSets are described for databases and message brokers, which can use either internal K8s storage (via CSI) or connect to existing PostgreSQL or Redis clusters within the customer's environment.

- Network Policies. At the Kubernetes level, any outbound requests to the external network are strictly blocked. An important caveat: policies require a CNI with support for them (Calico, Cilium) – on plain Flannel, the manifest will apply and do nothing; this should be verified with a test. All operations occur strictly within the private environment.


2. Agent Orchestration: How AI Employees Communicate with Each Other

The essence of Agentic AI lies in the division of responsibilities. A single universal agent cannot effectively solve complex business tasks without hallucinations. In "Archangel," the task is broken down into subtasks performed by specialized AI agents communicating through an asynchronous data bus.

We built the orchestration based on the Event-Driven Architecture (EDA) pattern. The role of the central nervous system is performed by an internal data bus (Event Bus) deployed within the cluster.

End-to-End Example of a Multi-Agent System in Operation

Let's consider a real business case: a large company uploads a complex contract project to the system for risk analysis.

1. Ingestion Agent. Parses the document, cleans the text from noise, and sends a document.parsed event to the data bus.

2. Legal Agent. Subscribes to this event, takes the text, performs semantic analysis, and finds a hidden legal conflict (e.g., incorrectly described penalty clauses). It publishes a structured message collision.detected to the Event Bus.

3. Finance Agent. Reacts to the collision event. Its task is to calculate the potential financial risk in monetary terms based on the company's internal historical data. It performs the calculation and sends a risk.calculated event.

4. Integration Agent. Collects artifacts from the previous agents, aggregates the data, and forms the final strictly validated JSON response for the customer's ERP system (or CRM systems like 1C / Bitrix24).

Thanks to this approach, agents do not block each other, and the system itself scales horizontally easily: if the number of legal documents increases, Kubernetes simply spins up additional pods with the legal agent.

3. Security of Vectors and RAG: Local Knowledge Base

To reduce hallucinations and ensure AI agents operate with the company's current context (regulations, policies, document archives), we use RAG (Retrieval-Augmented Generation) technology.

In cloud solutions, your documents are sent to third-party services for vectorization and storage. In "Archangel," this process is completely localized.

Vector Layer Security Architecture:

- Local Embedding Models. Text is converted into a vector representation (numerical arrays reflecting the meaning of phrases) on dedicated GPU nodes within the same Kubernetes cluster using lightweight open-source models (e.g., based on the BERT architecture). Not a single byte of text leaves the environment.

- Isolated Vector Storage. Generated vectors of regulations and internal company knowledge are stored in a specialized vector database (e.g., pgvector, Qdrant, or Milvus) deployed nearby.

- No External Synchronization. The knowledge base resides within the same isolated environment and is fundamentally not synchronized with cloud providers. Knowledge base updates occur locally: when the internal compliance department uploads a new regulation, the system locally re-indexes it and updates the vector indexes.

The AI agent accesses the company's "memory" through a fast internal API request to the vector DB, retrieves the necessary context, passes it to the local LLM, and provides the result with links to specific sources – the final decision remains with the lawyer.

Conclusion

Creating Agentic AI for the Enterprise is primarily an infrastructure and security challenge, and only then a Data Science one. By wrapping the platform in Helm charts, configuring event-driven agent interaction via an Event Bus, and isolating vector databases, we have created a system that operates predictably and does not require a single outgoing packet beyond the perimeter. I won't call it absolutely secure – such things don't exist – but the attack surface here is fundamentally different from cloud integration, and this is precisely what customers from regulated industries pay for.
