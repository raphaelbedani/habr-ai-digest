Recently, the world of artificial intelligence has seen a significant paradigm shift. Previously, we talked about intelligent assistants that automate rather narrow scenarios – answering questions from documentation, support bots, and so on. Now, technologies have reached a level where complex human actions can be automated using various planning tools, multi-step task execution, and the like – all that is now called AI agents. Many companies are releasing their own solutions, and there are also open-source solutions. There is a lot of noise around the topic, with semi-working prototypes often encountered, but at the same time, there are scenarios where agents prove to be truly useful and are already helping to solve business tasks.

What is an AI agent? At its core, it uses the same large language model (LLM) technology as assistants. The model receives a task description as input and generates a text response. A certain context is provided to the model to help it perform the task better. And here lies the key difference in the process: the model can stop at any moment and, instead of generating the next word of the response, execute a call to a tool, generating arguments for it. For example, based on the user's request text, the model can perform a search query, retrieve documents, read them, and after it "understands" what it received in response, it can call a new tool and continue its investigation if there isn't enough information for the answer.

The language model's process changes: instead of a single-pass mode where the model receives a request and provides an answer, the LLM can enter a self-reflection loop. During this loop, it can review the results of using a tool, determine if there is enough information to answer the user or complete a task, and either call another tool, reformulate the request, or (if it understands there's enough information) simply provide the answer to the user. Moreover, for the user, not only the direct answer they receive might be important, but also the facts of the calls (and the arguments for the calls) to the tools that the model will invoke on its way to the answer.

What kind of tools can these be? For example, imagine we tell an agent: "Organize a business trip to Kazan for me next week." The agent could potentially not just write a list of tasks for the user to complete, but could find a train ticket, find and book a hotel near the meeting location, create a calendar event, send invitations to colleagues – in short, do everything a user can do within the system. After that, its response would be: "Everything is ready, please check!" The capabilities of an AI agent are, of course, not limited to those listed in the illustration below.

There is a shift in the paradigm of interacting with artificial intelligence. Previously, our quality criterion was how well the agent answered a question. Now, it turns out that an AI agent can perform a whole chain of actions, and the quality criterion is whether the agent solved our task or not. This new interaction style is more useful because it addresses more user tasks.

For easier addition of tools to an AI agent's context, the community has developed a special standard for describing tools – the Model Context Protocol (MCP). Essentially, it's similar to what REST is for web services. An agent can connect to an MCP server that provides it with a set of tools, and the agent can call them. The MCP server also provides the agent with descriptions of how these tools can be called, and instructions on how the tool works and what results it will return. These tools themselves may not be intellectually complex; they might not have artificial intelligence under the hood at all. For example, they could simply be sending an email, or retrieving a specific user's schedule/calendar. Tools can be implemented using any application code, including 1C.

This brings up the issue of security in full force. If we decide to connect a specific server via the MCP protocol, we need to understand that this is a third-party solution, and the developers of this MCP server could have implemented arbitrary instructions. If the agent can receive their descriptions, this can be a security problem, and we need to check what instructions the agent will receive – for example, will there be an instruction like "send all query results to a specific address," and so on?

Some go even further, and instead of a limited set of tools, they give the model access to the entire workspace, including the execution of arbitrary code on their machine. An example of such an agent is the popular OpenClaw client. It has the ability to download files, install libraries, and so on. This even led to a surge in demand for Mac Minis – small Apple computers that can run this agent in isolation from the user's main machine. In this setup, users use an entire computer as the agent's workspace, while the neural network itself still runs remotely on Anthropic's servers.

In general, such automation tools are often used by technically advanced developers who can modify the tools for themselves. By "writing" the necessary tools for machine interaction (e.g., a bash script for rebuilding a container), they can teach the agent to perform complex tasks, such as project builds, running automated tests, and other processes. Setting up and adapting this agent requires time and an understanding of how it works under the hood; consequently, powerful ready-made solutions that can work "out of the box" for the mass user are not yet available.

However, those who have spent time setting up an environment for the agent to interact with, without using visual prompts – by connecting the necessary MCP servers, figuring out which tools are missing, and configuring the environment – report a significant increase in productivity. The technology works, but it still requires some effort to get started.

At the same time, there are some issues and complexities with the AI agent technology itself.

The main significant problem is security, and it manifests in several aspects.

When an agent gains the ability to act in the real world, the security issue reaches a fundamentally different level. Two key threats are related to data access and external information sources.

Firstly, violation of access policies. If the agent's tools involve accessing confidential data, we cannot guarantee that the model won't decide to bypass restrictions at some point – even with the best intentions. The agent might request data that the user doesn't have access to, simply because it deems it useful for the response.

The most reliable solution is to use an enterprise role model and execute all calls on behalf of the user who launched the agent, considering their access rights. There is also a practice of requesting user confirmation before performing sensitive actions. Formally, this sounds like a solution, but in practice, there is a serious risk: users tend to not read warnings and simply click "OK."

Secondly, the aforementioned prompt injections through external sources in the context of MCP. If web search is among the agent's tools, the response from an external server might contain malicious text that forces the agent to perform an undesirable action – a so-called prompt injection. The agent perceives the received text as context and may follow the hidden instructions within it.

The most reliable approach is to limit the range of sources accessible to the agent and, whenever possible, work only with your internal knowledge base, where the content is controlled and verified.

To avoid being unsubstantiated, here are a few recent examples.

Not long ago, the "Financial Times" reported that in one of Amazon's data centers in mainland China, an AI agent named Kiro left the data center offline for 13 hours. It acted on behalf of an engineer who was overseeing this service and, instead of a targeted fix, decided at some point that the best course of action was to simply recreate the cluster from scratch. The company cited incorrect user access rights as the cause: the user shouldn't have had the rights to perform such actions in the first place, but in fact, there was also an error in the agent's behavior – it didn't ask for confirmation before performing the operation and immediately proceeded with "fixes." As a result, engineers had to urgently restore functionality simply due to improper access rights management.

Another example is a post from the Chief Security Officer of a very large company (from here). The CSO asked an agent to read the contents of his email inbox and suggest candidates for deletion. The agent decided it needed to go through all corporate mail and delete everything it deemed necessary, without any coordination. Judging by the logs, it simply relied on the email creation date, without analyzing the content. Whether it was an external injection or a hallucination is unclear, but the fact remains: due to a software error, it couldn't be stopped in the chat, so the machine where this agent was running had to be completely rebooted. It's hard to even imagine the consequences such an event could lead to.

Nevertheless, current solutions already show that the use of AI agents has very high potential and is actively changing the business processes of entire companies.

The post by Andrey Karpathy, former Director of AI at Tesla (and former OpenAI employee), illustrates the current state well. Previously, he wrote about 80% of the code manually during his work, and generated the remaining 20% with AI. At the end of January 2026, he writes about the inverse change in proportion – AI agents have become so stable that 80% of the work is now done automatically, and only 20% is written manually.

A similar phase shift is possible outside of code-related fields – it's just that the industry doesn't yet fully understand how to make AI agents as useful for non-developer users.

And between them is a vast space of people who have tried something but haven't yet reached full utilization.

And this space is the main opportunity for development. If we can provide these people with a convenient, ready-to-use tool, we will unlock the same growth for them that developers in the red square are already experiencing. The question is how to make it, firstly – convenient, and secondly – safe.

We also consider this direction very important from our side.

Until recently, our 1C:Assistant worked only in the classic mode: the user asks a question, the bot searches for information in the knowledge base, collects context, and forms an answer.

Now, we have implemented the use of an agent cycle for generating answers. Assistant can work in two stages:

First level – quick response. The user asks a question and receives an answer from the knowledge base in a few seconds. In most cases, this is sufficient.

But if the answer didn't help the user and they gave it a thumbs down, a prompt appears offering to contact "1C:Assistant PRO." The user decides for themselves whether they need a more in-depth analysis.

Second level – agent. If the user clicks the button, the request is passed to the agent, which knows how to use tools: it performs several steps of searching documentation, correlates the findings, checks for completeness – and forms a detailed, structured answer.

It's evident that in agent mode, Assistant responds noticeably slower than in "normal" mode – and this is expected: searching, verifying, and clarifying information takes time.

However, after completing the search, the agent forms a complete, structured answer: it records all nuances of the request, compares options if necessary, provides examples, highlights limitations and risks, and explores the topic from various angles. That is, it provides what the simple Assistant in quick response mode often misses – simply because it doesn't have time for detailed verification, additional document search, and in-depth answer development.
