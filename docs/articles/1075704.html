Where the Model's General Knowledge Ends

The problem isn't that the model doesn't understand how an interface is structured. It knows that a container can be made with flex, a status can be shown with a badge, and data can be laid out in cards. But general UI patterns don't reveal the contract of a specific design system.

At the bank, we use FCC UI. This is a UI kit for React with primitives, cards, modals, drawers, and controls of all kinds. For example, a flex container in FCC looks like this:

<Flex direction="row" gap="s2" alignItems="center">…</Flex>

Here, direction controls flex-direction, alignItems controls align-items, and gap retains its familiar meaning. A model without context will likely assemble the same container on its own:

const StyledContainer = styled.div`

 display: flex;

 flex-direction: row;

 align-items: center;

`;

If the stars align in a particularly peculiar way, we get this result.

<div style={{ display: 'flex', flexDirection: 'row', alignItems: 'center' }}>
  The stars aligned
</div>
<div style={{ display: 'flex', flexDirection: 'row', alignItems: 'center' }}>
  And we got this result
</div>

The same happens with colors, sizes, icons, and component composition. The model might recall a similar API from another library and confidently insert it into FCC.

In the best-case scenario, the agent will find TypeScript declarations in node_modules and try to reconstruct the contract from them. Types will suggest which components exist and what props they accept. But they don't always reveal which component to choose, how to compose it, and what pattern is currently considered correct in the project. Such code might work, but it doesn't adhere to the contract and agreements of a specific project.

Giving the Agent Access to the FCC Contract

To avoid discussing the problem abstractly, I took a test project with two packages. @fcc/ui contains interface components, and @fcc/icons contains design system icons.

For example, a task might require displaying a product category and status in badges. It's not enough to understand that a green badge is needed. The agent needs to know that in FCC, Badge has a color prop with a fixed set of values and a semanticColor prop with semantic tokens. Then, it needs to select the existing component, the correct prop, and an allowed value.

I provided access to the up-to-date contract through the design system's MCP server, docs-context. Through it, the model can:

  • find an existing component using list_components;

  • get its props and allowed values via get_component_props;

  • view real usage examples in get_component_stories;

  • select an icon via get_icons;

  • find a semantic color token using get_colors.

In practice, the agent first finds a suitable component, then checks its API, and only after that looks at composition examples. Unlike a regular documentation search, MCP provides structured facts about the contract. Models don't have to guess which components exist, what values are allowed, and what tokens are available.

And so, I solved the problem... Or did I?

Why an MCP Skill?

If the model can ask what components and props exist, why add another layer?

I created a skill that pre-sets the model's principles for working with the design system:

  • use FCC components and icons;

  • do not invent component, prop, or token names;

  • do not use third-party UI libraries;

  • do not assemble visual primitives from scratch if FCC already has a suitable component;

  • do not write inline styles;

  • do not use HEX colors instead of tokens;

  • refer to MCP when needing to check a component, prop, icon, or color.

The skill does not store a list of components or duplicate MCP. It sets the intention and boundaries of acceptable behavior. But intention alone is not enough. Even knowing that props cannot be invented, the model can still make mistakes. The skill requires checking the contract, but doesn't provide the exact prop name itself.

In all four modes, the task remained the same. For each, I used a separate project copy and a new model session. All data, products, and conditions are fictional and do not represent an actual offering.
