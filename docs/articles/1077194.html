What Routine Tasks Consume an Analyst's Time

Let's take a look at a typical workday of a data analyst who creates a data mart. Here's how this process looks in a traditional approach.

It all starts with an epic in Jira. The analyst receives a task, but the technical specification is usually vague. Clarifications begin: running to the client, asking questions, trying to extract clear requirements from the business. The client, naturally, is not very happy with all this. Then the analyst creates various prototype artifacts (specification, prototype script, DDL, all this is agreed upon with the naming convention, etc.) – most often, all this is done based on experience, from memory. Some write it themselves immediately, while newcomers go to seniors to clarify something and spend not only their own time but also the time of expensive employees.

Then the search for templates in Confluence begins. The problem is that templates can be outdated; someone maintains them, and someone doesn't. After that, the analyst manually writes down the requirements from the task description, agrees on the documentation with the team, product manager, and data stewards. And finally, corrects errors after code review.

Here's how, according to our calculations, an analyst's work time is distributed during the day:

  • Information Search — 25% of the time. The analyst searches for the necessary data in Jira, Confluence, and by asking colleagues.

  • Documentation Creation — 30%. This includes DDL scripts, business requirements, specification descriptions, and prototypes.

  • Approvals and Revisions — 20%. Approvals with the team, data stewards, product manager, and correcting remarks after review.

  • Direct Analysis and Design — only 25%. This is where the analyst uses their brain, critical thinking, and expertise.

This means that only a quarter of the analyst's workday is spent on actions that truly require their qualifications. Everything else is searching, formatting, and approvals. And this is where the question arises: can this work be delegated to AI? If so, what tools – skills – are needed for this?

What are Skills in Our Context

When we talk about AI in the context of an analyst's work, it's not about "giving a task to a neural network and getting a result." We're talking about a systematic solution that needs to be scaled and used repeatedly.

In our case, a skill is not a typical prompt, but a saved, reusable scenario for a neural network for a specific type of AI agent task. Such a scenario has:

  • a clear description of the role and task (who performs it, what needs to be done);

  • a step-by-step execution algorithm (in what sequence to act);

  • requirements for input and output data (what is fed in, what should be received);

  • examples and templates (the neural network understands what the result should look like).

A skill is a complete working instruction for an AI agent. It doesn't just answer a question – it performs a sequence of actions, interacts with corporate systems, and creates artifacts.

And here's an important point: a skill doesn't exist in isolation. It works in conjunction with an AI agent that executes the scenario, and with an MCP server that provides access to systems.

What is an MCP server? It's a driver – a middleware between the agent and corporate systems. It allows the agent to connect to Jira, Confluence, GitLab, databases, APIs, and other sources. Without an MCP server, the agent simply won't see the data it needs to work with. With it, it can read tasks, extract templates, check naming rules, and save results. Everything is centralized through a single interface.

And one more important nuance: one agent can possess multiple skills, and one skill can be used by different agents. It's like a library of functions, where each function knows how to do something specific, and you call it as needed.

Why We AI-ified Analyst Work

We implemented AI tools into the work of data analysts and simultaneously measured the effect. We achieved tangible benefits:

  1. Speed. AI writes quickly. It creates not just text, but structured artifacts that can be used immediately: DDL scripts, YAML specifications, business requirements based on a template. The time to create them is reduced by 3–5 times, and in some tasks – by 20 times. Our developments already show such results: creating business requirements takes 30 minutes instead of 8 hours manually.

  2. Consistency. Different analysts may format documents differently. Each has their own style, their own preferences. Some prefer tables, some lists, some detailed descriptions. With the use of AI, all artifacts are created according to a single template. This simplifies both reading and further automation.

  3. Scalability. An analyst freed from routine can handle multiple projects in parallel. Quality doesn't suffer – AI handles the routine work, and the analyst controls the result.

  4. Quality. Humans make mistakes. We all know how difficult it is to find an error in DDL or field mapping. AI, if configured correctly, makes fewer such mistakes. Yes, it can also err – hallucinations are not to be dismissed. But we can make it learn, check its own results, and gradually reduce errors.

  5. Onboarding. This is a non-obvious but very important point. A new employee, using agents and their skills, immediately begins to understand how processes work. They see templates, see the expected result, and learn by doing. They don't need to sit next to a senior and memorize how to format business requirements correctly. They simply launch the skill and see the standard.

What Processes Can Be Automated, and What Cannot

We divided all analyst tasks into three categories based on their automability.

Fully Automatable (80%+ via AI)

These are tasks that are performed according to a clear algorithm, have structured input and output, and for which ready-made templates exist:

  • Extracting requirements from Jira and Confluence. The skill reads the epic and related tasks, extracting all necessary information.

  • Generating DDL from a template. AI creates scripts with technical fields, comments, and descriptions.

  • Creating CSV and YAML specifications. Machine-readable formats for other agents.

  • Checking compliance with naming rules. If you have defined rules, AI will check if everything complies with them.

  • Searching for similar data marts in the repository. To avoid reinventing the wheel if something useful has already been done.

Partially Automatable (50–80% via AI)

Here, the result requires human verification and refinement:

  • Creating business requirements from a template. AI generates a structured document, but it needs to be cross-checked with the original technical specification.

  • Source-to-target field mapping. AI suggests mappings, but the analyst verifies if everything is correct.

  • Analyzing data gaps. AI highlights inconsistencies, but the final decision rests with the human.

  • Generating test data. Synthetic data is generated without problems, but from a security perspective, one needs to check what the AI has done.

Require Human Involvement (<50% via AI)

Here, AI can only assist:

  • Approving requirements with the business. You need to talk to the client, clarify, delve into details. AI is not helpful here. We tried to implement AI for such communication – for gathering requirements, for clarifying vague technical specifications. But the business speaks its own language, different teams have very different approaches, and AI cannot yet bring this to a common denominator.

  • Making architectural decisions. Architecture involves costs and has long-term consequences. A human is definitely needed here.

  • Prioritizing tasks. AI doesn't always know who is most loaded on the team, who is in a crisis right now, and who has already finished everything. This coordination process is for the analyst.

  • Interpreting business context. The business may formulate a task in such a way that no AI can understand it without hints and explanations.

The key principle we derived for ourselves is that AI is a tool to augment the analyst, not replace them. It takes over template-based, repetitive, structured work. Everything that requires creativity, negotiation with the business, and decision-making remains with the human.

How We Determine if a Task Can Be Automated

We have identified four criteria. If a task meets them, it can be safely delegated to AI.

  1. Repetitiveness. The task is performed according to the same algorithm. If you do the same thing every time, it's a candidate for automation.

  2. Structuredness. Input data has a clear format. You know what you're feeding in, and you know what you want to get out.

  3. Documentation. There are clear rules and templates. If you cannot unambiguously describe the process, AI certainly won't be able to perform it.

  4. Verifiability. You can define quality criteria. If you don't know how to check the result, you won't know if the AI is working or not.

If at least one of the criteria is not met, it's better not to automate. Where there is ambiguity or where it is difficult to measure the result, a human will cope better.

How We Evaluate Skill Quality

We have developed a three-level evaluation system. Without it, it's hard to tell if the AI is working or just producing pretty text.

Level 1 — Format Validation

This is the most basic check. We look to ensure that:

  • All output files are created (not missed).

  • YAML and CSV are valid – they parse without errors.

  • DDL is syntactically correct (can be run in the database).

If this level is not passed, there's no point in looking further. A format error makes the result useless.

Level 2 — Consistency Check

Here we check that the result complies with the rules:

  • Field names comply with naming rules from Confluence.

  • All mandatory technical fields are added (creation date, update date, flags, etc.).

  • Mapping to sources is complete – no fields without a source.

If problems are found at this level, they are easier to fix than if the analyst had to find them manually.

Level 3 — Business Validation

This is the most complex check. It requires understanding the business context:

  • Requirements from the epic are fully reflected in the business requirements.

  • Acceptance criteria are measurable and testable.

  • Use Cases cover the main scenarios of use.

A human is indispensable here. But AI helps: it has already prepared the structure, and all that's left is to check that nothing has been missed.

What's Next

Skills are already showing results, but we intend to develop the system further – here are the key directions:

Data Catalog Support. We want to add integration with DataCatalog and DataContract – so that all metadata about data marts is stored centrally and is accessible to other agents.

Automatic DDL Validation. Currently, we check DDL manually. This can be automated: run the generated script in a test database, check that it executes without errors.

Unit Tests for ETL Processes. If we have a specification and DDL, we can automatically generate tests for data loading.

Artifact Transfer Between Agents. Skills can already transfer context. We want to develop this further: so that agents can decide themselves who to transfer intermediate results to and automatically start the next stage.

Quality Monitoring. We plan to create a dashboard with metrics for skills: how long generation took, how many tasks were processed, percentage of errors. To see where skills are working well and where they need improvement.

Learning from Mistakes. We collect feedback from the team and use it to retrain agents (fine-tuning based on specific examples).

Let's Summarize

  1. AI automation is about augmenting the analyst, not replacing them. We are not eliminating people. We are eliminating routine. The analyst spends time on analysis, not on document formatting. AI takes over up to 80% of template-based work.

  2. Skills work like a pipeline. These are not isolated tools, but a connected chain. Each stage passes context to the next. An Epic in Jira turns into business requirements, these into a physical model, that into DDL and mapping. All automatically, without manual data transfer.

  3. MCP server is a useful component. It provides integration with corporate systems without external dependencies. It runs locally and gives the agent access to Jira, Confluence, GitLab, and other sources. And if your security requirements allow, you can add external sources, databases, and anything else.

  4. Quality is measurable. We don't implement AI blindly. We have clear metrics for each skill, standard examples, and an audit system. We see where skills work well and where they need improvement.

  5. There are tasks that AI cannot replace. Negotiations with clients, interpretation of ambiguous requirements, architectural decisions with long-term consequences, prioritization in resource-constrained environments – an analyst is needed here.

We are testing skills on our projects. Not everything works perfectly yet – much depends on the quality of input data, on how the technical specification is formulated. But where it is well-written, the result is impressive.

A well-written AI agent with configured skills is a great help for a data analyst. It saves time, protects against a range of errors, and makes the team more efficient. But it doesn't solve all of an analyst's tasks. Creativity, negotiation, understanding context – all this remains.
