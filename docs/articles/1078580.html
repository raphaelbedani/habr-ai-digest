On Android devices, you can choose a default assistant, much like a browser. Once selected in settings, you can invoke it with a system gesture over any app. Convenient.

You might think that the chosen assistant can now see everything on your phone and do whatever it wants... Not at all. When installed, Android grants an app only basic permissions. Access to advanced features requires separate user permission, and some functions are entirely unavailable to regular third-party apps.

My name is Vanya, I lead the Android development team for Alice's SDK and am the tech lead for the default assistant project. Today, we'll explore these boundaries using Alice AI as an example.

What Changes After Selecting a Default Assistant

Not just any chatbot app can become an Assistant. Developers must add support for this role, and the user must manually select the app as the default assistant in system settings. The app can help open the necessary settings screen, but only the user can choose the assistant.

Along with the role, Android can grant the assistant several technical permissions if the app has declared them in its manifest. For example, in Android 17, SYSTEM_ALERT_WINDOW is tied to the role, allowing the assistant to display its window over other apps, and EXECUTE_APP_ACTION, to access actions that third-party apps have allowed assistants to use.

These permissions by themselves do not allow access to the microphone, camera, contacts, or geolocation. They also do not give the assistant free rein to read data from other apps. Other assistant capabilities depend on different Android mechanisms. Let's examine what information the system passes about the open screen, what permissions the user grants manually, and how the assistant interacts with other apps.

What the Assistant Learns About the Open Screen

Assigning Alice AI as the default assistant does not grant it constant screen access. Android collects screen context only after the user explicitly opens the assistant over a specific app screen.

At this moment, Android can transfer the interface structure and visible text (AssistStructure), data that the open app has prepared for the assistant (AssistContent), and a screenshot. This is not a video stream or access to the app's internal data, but rather information about the state of the open screen.

The open app can restrict the information transferred. For example, a window with the FLAG_SECURE flag prevents a screenshot from being sent. The assistant cannot independently read the content of any screen, monitor transitions between apps, or obtain screen context in the background. By the way, an important clarification: on the lock screen, Android hides notifications before opening the assistant. Therefore, you cannot read them through the screen context either.

Screen context is only one source of data. Let's explore how other access is granted in the next section.

For instance, in the standard location request, the user chooses which coordinates to grant Alice AI access to: approximate (ACCESS_COARSE_LOCATION) or precise (ACCESS_FINE_LOCATION). Starting with Android 11, permission to work with location in the background (ACCESS_BACKGROUND_LOCATION) is granted separately. Alice AI can open the relevant settings screen, but the user must select the "Allow all the time" option. Being the default assistant changes nothing here.

The command "Call Sasha" consists of two operations. READ_CONTACTS allows finding Sasha's number in the address book, and CALL_PHONE allows initiating a standard phone call immediately. This won't work with emergency numbers. For direct dialing without confirmation, the system permission CALL_PRIVILEGED is required, which is unavailable to regular third-party apps. It cannot be granted to Alice AI in settings, even if it's the default assistant. Alice AI can only open the dialer app with the correct number, and the user must confirm the call.

The POST_NOTIFICATIONS permission on Android 13+ allows Alice AI to display its own notifications. It does not grant access to other apps' notifications, and Alice AI does not currently receive them.

How the Assistant Executes Commands in Other Apps

An assistant can execute a command in another app only if that app provides a suitable interaction method. Being the default assistant does not create a universal remote for all installed programs.

For common actions in Android, there are Intents—a standard way to pass a request to another app. For example, via ACTION_SET_ALARM, the assistant can pass the time for setting an alarm to the clock app. The clock app will either show the user a pre-filled form or create the alarm directly—this depends on the system app's implementation.

Universal intents are not available for everything. For instance, for Google Assistant to perform an action within a third-party app, its developer must describe that action via Google App Actions. Third-party assistants do not automatically get App Actions—even after being set as default. First, it must declare EXECUTE_APP_ACTION in its manifest, and only then can Android grant the permission along with the role.

In Android 16, a more general mechanism, AppFunctions, was introduced. Its public API is still experimental, and each app decides independently which functions to allow for use.

Another mechanism is control through interface elements. This is how Accessibility Services work: they can read available elements on the screen and perform clicks. This is not hidden access: the user manually enables such a service for a specific app on a separate system settings screen, and Android warns about its capabilities.

The use of AccessibilityService is monitored separately by Google Play. The developer must declare the use of the service and pass a review. If the app is not an accessibility tool, it must explain what data it receives and why, and then request explicit user consent.

Simply put, an assistant can control another app only through a mechanism provided by Android or the app itself: a standard intent, a published function, or a manually enabled accessibility service. Alice AI controls Yandex Music and Yandex smart home devices through its own product integrations, and sets timers and alarms via Android intents.

Why Some Assistant Commands Are Unavailable

The first limitation is the Android sandbox. Apps run in isolation, so the assistant role does not grant access to the internal data of banking apps or messengers. For exchange, a provided channel is needed: a system intent, an exposed app component, or a service API.

The second limitation is that some system permissions are unavailable to regular apps. Designating an app as the default assistant does not make it a system app or grant it such permissions.

The third limitation is support from the other application. The assistant cannot execute a command if the app does not accept the standard intent, does not publish the required function, and does not provide its own API.

These limitations cannot be removed by selecting the assistant as default or by toggling a setting. They are defined by the Android architecture itself and the capabilities of other applications.

What's the Result

So, what does choosing a default assistant give you? Android will open the selected app with a system gesture and grant it access to available information about the current screen.

Alice AI remains a regular app installed by the user. Access to the microphone, camera, geolocation, and contacts is granted separately by the user. Without these permissions, Alice AI will continue to function as an assistant—you can still ask it questions via text. Background geolocation is enabled on a special system screen, and controlling other apps requires mechanisms provided by Android or the apps themselves.

Some system capabilities remain inaccessible to regular apps, no matter how many permissions they are granted. Being set as default makes interacting with Alice AI more convenient, but it does not change Android's security model: the assistant does not gain full access to the smartphone.
