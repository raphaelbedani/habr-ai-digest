Hi! I'm Vladimir Mokrousov, a system administrator at the Synteka group of companies. We develop software for the construction industry and actively use AI models in our work.

Recently, we created a unified access to models based on LiteLLM. In this article, I'll tell you how we built this system, what pitfalls we encountered with limits and blocks, and what we had to control to make it all work.

Why We Built a Unified Gateway

Initially, each department bought its own subscriptions to OpenAI, Anthropic, and DeepSeek, but managing accounts and limits became increasingly difficult and costly. We decided to switch to a unified gateway and deployed LiteLLM.

Essentially, LiteLLM is a router: through it, we divide users into groups, give employees access to models, and monitor logs. If errors appear or limits are exhausted, we investigate here.

Here's how the new system works when accessing a model:

  • Via Subscription/OAuth. In this case, an additional layer is needed between LiteLLM and the provider – this is CLIProxyAPI. We connect provider accounts to it and specify the API key here. CLIProxyAPI can handle multiple subscriptions and monitor their limits.

  • Via a Regular API Key. Here, LiteLLM communicates directly with the provider. We couldn't connect everything via subscription: it turned out to be possible only for any Anthropic model, and at OpenAI, many tools are only available via tokens.

As a result, the system solved two major problems.

Gained control over subscriptions and limits. Each team now has its own restrictions. We can control resource consumption and quickly reallocate them between departments if one is overloaded.

Simplified access for teams. Now an employee doesn't need to deal with a bunch of accounts: they get a server address and a single API key for a set of models. Then they use it in their familiar tools – for example, in Claude, OpenCode, Reactor, Codex, or their own code.

Everything seemed fine, but we were about to hit some major roadblocks.

Encountered Implicit Limits with Anthropic

We connected Claude via subscription: it's easier to forecast the budget this way. However, when paying per token, costs directly depend on the volume of requests, so company funds quickly drain with active model usage.

With Anthropic's subscription, we initially focused on two limits – for five hours and for a week. But in practice, it turned out to be more complex: the consumption is affected by the chosen model, context length, tools used, and current load.

When our employee was actively working with Opus 5, we received a message that Extra Usage had run out. It turned out to be a separate paid quota that is consumed independently of the main subscription limits.

Additionally, we found separate limits for specific models. For example, the new Fable 5 model has its own limit. We haven't used it yet, just planning to try. Importantly, exhausting the limit of one model does not mean that others will become unavailable.

So, it's important to distinguish our experience and API response facts from Anthropic's official rules. For organizational use, it's more reliable to choose the official API or a corporate contract rather than combining personal subscriptions.

Got Two Account Blocks in a Row

Account blocking is a similar story: we also encountered non-obvious reasons that providers don't officially write about. Here's what our experience with OpenAI and Anthropic showed.

OpenAI Blocks. It happened like this: we paid for several accounts with one card, and at some point, the account was blocked. Currently, we have three OpenAI accounts connected in CLIProxyAPI. They work fine: limits are consumed and balanced between them.

Anthropic Blocks. It went differently here. We connected two personal accounts to one CLIProxyAPI. The new one was immediately blocked without explanation. 

Then we created a new account and connected it to CLIProxyAPI. Half a day later, it was also blocked. We don't know why this happened. I've encountered a theory that Anthropic also looks at the age of the Gmail account: if the email was recently created and an account was immediately registered on it, it might look like bot behavior. But this is just a hypothesis.

I note that the requests came from a single IP, its geolocation matched the account's registration country and the bank card's issuing country. That is, we found no obvious reasons for the blocking.

As a result, we now maintain at least two working Anthropic accounts so that the blocking of one doesn't leave employees without access to models.

Couldn't Connect New Models with the Old Scheme

When Claude released new models Sonnet 5, Opus 5, and Fable 5, we added them the same way as the previous ones. But it didn't work.

It turned out that the release of a model doesn't mean the current version of LiteLLM supports it. You need to update the image or configure the route differently. In our case, we had to adjust the route for Anthropic, after which the models started working.

Next, we proceed step-by-step:

  • Determine the access source. Subscription access works through CLIProxyAPI. A regular LLM provider API key is configured directly in LiteLLM without CLIProxyAPI.

  • Specify the adapter and address. New Claude models are connected via anthropic/<model> with a base address of 0.0.0.0:8317 without /v1. Old models continue to work via openai/<model> at 0.0.0.0:8317/v1.

  • Verify before publishing. After updating or changing the route, you need to test a regular request.

    In the end, to connect a model, four matching elements must be correctly configured: model ID, provider adapter, base URL, and authorization method.

Started Investigating Error Causes

In our system, a failure can occur at different levels: in the request, LiteLLM, or on the provider's side. We've identified several patterns that help quickly find the cause by error code. Here are the common errors we encounter.

Error 400: Bad Request. It could be due to incorrect message formats or roles, prefill, tool calls, or an inappropriate API endpoint.

Errors 401 and 404: Unauthorized and Not Found. These usually appear when employees manually enter the model and make typos. The error could be due to an incorrect key, base URL, alias, or route.

Error 429: Too Many Requests. Usually means the quota is exhausted, a cooldown period is active, or all accounts are temporarily unavailable.

Errors 500 and 503: Internal Server Error and Service Unavailable. These are recent, and we haven't fully figured them out yet. Most likely, such an error can occur due to provider overload, streaming interruption, authorization issues, or inability to switch to a backup model. Another possible reason: insufficient resources on the server where our CLIProxyAPI and LiteLLM are deployed.

How we find the source of an error:

  • First, we look not only at the HTTP code but also at the provider, model_group, request ID, and the nested upstream message.

  • We repeat the request directly to CLIProxyAPI or the provider, bypassing LiteLLM.

  • We simplify the request: disable streaming and tools, then re-enable functions one by one.

  • If the direct request is successful, we check LiteLLM's adapter and transformation. If not, we check authorization, limits, and access to the model itself.

The conclusion from our observations is that LiteLLM shows an error to the client, but its source can be at any layer of the system.

Learned to Manage Limits

Initially, everyone used shared resources, and limits in LiteLLM were exhausted very quickly. Therefore, we configured separate restrictions and access for each team (developers, testers, and analysts):

  • Provide a separate virtual key. This can be a key for each user, team, or service. We specify the owner and provide for revocation.

  • Set technical restrictions. We have an allowed list of models.

  • Set financial restrictions. We define a budget per period, track consumption, and provide warnings before exhaustion.

After this separation, we began to consume limits more evenly. Currently, Anthropic has been working for us for about a week without sharp consumption spikes.

Strengthened Data Protection When Working with LLMs

LiteLLM and CLIProxyAPI are deployed on a server in Turkey, accessible only from the corporate network. The services are not available from the outside – you cannot connect to them directly from the internet.

However, securing the gateway itself is not enough. Everything that employees send to the models, one way or another, goes to the provider. Therefore, we do not store keys in code or configuration, grant minimal permissions, and regularly rotate access.

And another rule – do not fully automate critical processes with models. In practice, I have repeatedly seen models choose the wrong path while solving a task. If you monitor their actions, you can correct the direction in time. Therefore, we are more in favor of a semi-automatic mode: the model does the work, and a human controls important actions and intervenes if necessary.

Instead of a Conclusion

LiteLLM has given us a single entry point for various models and clients and generally simplified working with them. However, the gateway itself does not guarantee stability – stability is achieved through correctly configured routes and authorization, restrictions, testing, and manual control.

Therefore, after setting up the infrastructure, the work doesn't end: you need to monitor limits, consider subscription specifics, deal with blocks, and check support for new models.
